## Phase 0: Spikes

Throwaway code, findings recorded in this file. Nothing merged except the findings.

1. **Crypto in every runtime.** `hpke` + `@panva/hpke-noble` with MLKEM768-X25519 / HKDF-SHA256 / AES-256-GCM, plus AES-GCM, HKDF and Ed25519. Check against the `draft-ietf-hpke-pq-05` test vectors in Chrome (native path and forced noble path must produce interoperable output), Firefox, Safari, Bun, and a Convex HTTP action and internal action on a local deployment. Record encapsulation time per runtime, bundle size against Convex limits, and confirm that queries and mutations can verify Ed25519 signatures.
2. **OPAQUE in Convex.** `@serenity-kit/opaque` 1.1.x server functions inside a Convex HTTP action (WASM import), client functions in the browser; Argon2id time on a low-end laptop and phone.
3. **Browser key handling.** A non-extractable key in IndexedDB survives reloads, is readable by the service worker and is gone after sign-out; the wrapped `sessionStorage` blob survives a reload, is gone when the browser tab closes, and is handed to a newly opened browser tab over `BroadcastChannel`; check per browser whether session restore brings the blob back (the last-activity time must then discard it).

Acceptance: each item has a recorded result and either confirms the design or names the required change to the design docs.

## Phase 3: Crypto Package, Key Records, Device Handling

- `packages/crypto`: envelopes, key capsules, AAD builder, padding, wrap/unwrap, signatures, safety numbers, and the [suite upgrade](../E2EE/Keys.md#suite-upgrades) machinery from the start: suite IDs on every record, key lists per purpose with certification by the previous key, and the key upgrade runner. Fixed vectors and tampering cases (wrong AAD, swapped capsule, truncated body, wrong suite).
- Schema in `packages/backend/src/keys/` with thin exports in `convex/keys.ts`: user keys, AMK wrappers, trust store, workspace keys, grants and phrase wrappers, invites, chat keys, key capsules, roster, Worker certificates, `e2ee_policy`, `key_upgrades`.
- Web key manager (`apps/web/src/lib/crypto/`): remembered keys by default, the require-password setting with the wrapped `sessionStorage` blob, device wrapping key and cross-tab `BroadcastChannel` coordination (hand-off, unlock, shared idle time, lock), auto-lock, Lock, the locked-but-signed-in Window.

Verification: a fake suite `99` defined only in tests goes through all four upgrade phases on two clients and a Worker, with pins carried over and no `changed` prompt. With the require-password setting on, in Chrome, Firefox and Safari: three browser tabs on different chats stay unlocked together; unlocking one unlocks the others; Lock in one locks all; closing all tabs and opening a new one asks for the password.

## Phase 4: OPAQUE In Radium

- Hooks and flows: sign-up with key bundle and recovery key confirmation, sign-in (also used to unlock), password change, reset page with recovery key, recovery from another unlocked device, and new keys (old key bundle retained).
- `auth:issuePasswordResetLink` internal action ([forgot password](../E2EE/Authentication.md#forgot-password)); `OPAQUE_SERVER_SETUP` and the reset procedure in [deployment](../deployment.md) and `.env.example`.
- Account migration screen and endpoint; classic credentials only reach that screen.

Verification against a local deployment: the password never appears in any request body (browser network capture); a password change keeps data readable; a reset link issued from the CLI works once and expires; reset with a recovery key and reset from another unlocked device both keep every chat readable, and the device secret never appears in any request; reset with neither yields new keys and locked personal data that a later recovery key restores; login with an unknown email is indistinguishable from a wrong password.

## Phase 5: Workspaces, Chats And Trust

Member and owner keys created by the owner's browser in the same mutation as the workspace, grants, access links with fragment secrets, the optional workspace key phrase, pending requests with trust prompts, trust store sync and rollback detection, safety numbers, signed roster, member removal with epoch rotation, re-granting by any key holder after a reset, chat keys and scope changes.

Verification with two real users on a local deployment: the member cannot open the owner's personal chat and vice versa, even with a client that skips the authorization check; replacing a member's public key directly in the database makes the owner's client show `changed` and refuse to grant; an access link works once, and neither its secret nor the workspace phrase appears in any request (network capture); clearing the owner's browser storage right after creating a workspace and signing in again recovers every key; removal blocks new messages for the removed member and invalidates the old phrase for the new epoch.

## Phase 6: Chatroom Content

Encrypted titles, attachments and queued prompts written by the client; `/api/aisdk/chat` keeps receiving the full AI SDK history from the client, with file parts carrying a file key; per-turn capsules for the persisted user message, assistant output and titles; message IDs and revisions in `saveChatMessages`; client-side title search; attachment download-decrypt-inline for providers; new chats while locked.

Verification: a full Chatroom turn with tools and an attachment; the Convex dashboard shows only envelopes in `chat_messages`, `aisdk_chats` and File Storage.

## Phase 7: Workers And ACP

Setup code `v2` with pairing secret, Worker encryption and signing keys and certificate, mutual pins; signed ACP commands and interaction answers; capsule-encrypted ACP frames; sealed session index (remove `search_title`); sealed Worker task requests, request-key results, sealed receipts, user-signed approvals and auto-approve grants.

Verification: an ACP session end to end with only ciphertext in `chat_frames`, `acp_commands` and `acp_interactions`; an unsigned command inserted directly into `acp_commands` is rejected by the Worker; an Edit tool call without a user approval signature is refused; a swapped owner key makes the Worker refuse commands.

## Phase 8: Telemetry And Notifications

Telemetry content sealed to the owner key with one capsule per request, keyed hashes (new deployment secret), client-side rendering and diffs, in-request content export, metadata-only scheduled export; sealed notifications and encrypted Web Push payloads with service-worker decryption when keys are remembered.

## Phase 9: Migration

Custody key in Secret Store; action-driven sealing migration with dry run and paginated verification, sealing to owners' keys where they exist and to custody otherwise; per-user and per-workspace release; operator query for custodial rows and the CLI mutation that ends custody; then a separate narrowing deploy. Nothing is deleted. Running it on any deployment needs explicit authorization (`AGENTS.md`).

Verification on a local deployment with seeded legacy data: a user who sets up encryption months later still reads every old chat; an unmigrated account recovered through a reset link keeps its content; the custody key can be deleted only at zero custodial rows.

## Later: Suite Upgrades

Each upgrade is one session using the procedure in [Keys § Suite upgrades](../E2EE/Keys.md#suite-upgrades); the machinery exists from phase 3.

**Suite 2: hybrid signatures (Ed25519 + ML-DSA-65).** Trigger: WebKit ships ML-DSA in WebCrypto, or the team accepts the pure-TypeScript signer everywhere.

1. Define suite `2` in `packages/crypto`: sign = both signatures, verify = both must pass; native ML-DSA through `SubtleCrypto.supports("sign", "ML-DSA-65")` with `@noble/post-quantum` `ml_dsa65` fallback; FIPS 204 test vectors in every runtime, including a Convex mutation (verification only).
2. Phase 1 (Read) deploy: verifiers accept suite 2. Ship web, Worker and backend.
3. Phase 2 (Add): enable generation in `e2ee_policy`; check `key_upgrades` until active users and Workers have certified suite 2 keys; spot-check that no `changed` prompts appeared.
4. Phase 3 (Prefer): switch writing to suite 2; the runner re-signs rosters, trust stores, Worker certificates and standing auto-approve grants.
5. Phase 4 (Require): after `key_upgrades` shows full coverage, reject Ed25519-only signatures.

Verification: mixed old and new clients during phases 1-3; an Ed25519-only forged command is rejected after phase 4.

**KEM encoding change.** If the RFC replacing `draft-ietf-hpke-pq-05` changes MLKEM768-X25519's encoding, the same steps apply with a new KEM suite; existing capsules are not rewritten.
