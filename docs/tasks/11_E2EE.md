## Phase 0: Spikes

Throwaway code, findings recorded in this file. Nothing merged except the findings.

1. **Crypto in every runtime.** `hpke` + `@panva/hpke-noble` with MLKEM768-X25519 / HKDF-SHA256 / AES-256-GCM, plus AES-GCM, HKDF and Ed25519. Record encapsulation time per runtime, bundle size against Convex limits, and confirm that queries and mutations can verify Ed25519 signatures.
2. **OPAQUE in Convex.** `@serenity-kit/opaque` 1.1.x server functions inside a Convex HTTP action (WASM import), client functions in the browser; Argon2id time on a low-end laptop and phone.
3. **Browser key handling.** A non-extractable key in IndexedDB survives reloads, is readable by the service worker and is gone after sign-out; the wrapped `sessionStorage` blob survives a reload, is gone when the browser tab closes, and is handed to a newly opened browser tab over `BroadcastChannel`; check per browser whether session restore brings the blob back (the last-activity time must then discard it).

Acceptance: each item has a recorded result and either confirms the design or names the required change to the design docs.

## Phase 3: Crypto Package, Key Records, Device Handling

- `packages/crypto`: envelopes, key capsules, AAD builder, padding, wrap/unwrap, signatures, safety numbers, and the [suite upgrade](../E2EE/Keys.md#suite-upgrades) machinery from the start: suite IDs on every record, key lists per purpose with certification by the previous key, and the key upgrade runner. Fixed vectors and tampering cases (wrong AAD, swapped capsule, truncated body, wrong suite).
- Schema in `packages/backend/src/keys/` with thin exports in `convex/keys.ts`: user keys, AMK wrappers, trust store, workspace keys, grants and phrase wrappers, invites, chat keys, key capsules, roster, Worker certificates, `e2ee_policy`, `key_upgrades`.
- Web key manager (`apps/web/src/lib/crypto/`): remembered keys by default, the require-password setting with the wrapped `sessionStorage` blob, device wrapping key and cross-tab `BroadcastChannel` coordination (hand-off, unlock, shared idle time, lock), auto-lock, Lock, the locked-but-signed-in Window.

Verification: a fake suite `99` defined only in tests goes through all four upgrade phases on two clients and a Worker, with pins carried over and no `changed` prompt. With the require-password setting on, in Chrome, Firefox and Safari: three browser tabs on different chats stay unlocked together; unlocking one unlocks the others; Lock in one locks all; closing all tabs and opening a new one asks for the password.

**Partly done (2026-11-08).** Built: `packages/crypto` (`radium-crypto`: suite 1 envelopes, capsules, AAD, padding, AMK wrappers, identity keys, Ed25519, fingerprints, safety numbers, phrases; native X-Wing/Ed25519 with noble fallback; RFC 5869/8032 and draft-ietf-hpke-pq vectors, tampering tests; 136 tests in Node and edge-runtime); account key records `e2ee_identities`, `e2ee_key_bundles`, `e2ee_device_recovery` in `packages/backend/src/e2ee/` with thin exports in `convex/e2ee.ts` (`convex/keys.ts` is the Gateway API keys module); the web key manager in `apps/web/src/lib/crypto/` with device wrapping key, remembered or `sessionStorage` blob, `BroadcastChannel` hand-off/unlock/lock, auto-lock, Lock, and the Window's Locked / "Encryption not set up" chip.

Not built yet: suite upgrade machinery (key lists with certification, `e2ee_policy`, `key_upgrades`, upgrade runner) and the trust store, workspace keys, grants, invites, chat keys, roster and Worker certificates; those tables belong with their consumers in phases 5 and 7.

Verified in Chromium only (isolated local deployment): with the require-password setting on, a second browser tab opened while the first is unlocked unlocks from the hand-off; Lock in one tab locks both; Unlock in one unlocks both; closing every tab and opening a new one comes back locked. Firefox, Safari and the fake suite `99` run are not done.

## Phase 4: OPAQUE In Radium

- Hooks and flows: sign-up with key bundle and recovery key confirmation, sign-in (also used to unlock), password change, reset page with recovery key, recovery from another unlocked device, and new keys (old key bundle retained).
- `auth:issuePasswordResetLink` internal action ([forgot password](../E2EE/Authentication.md#forgot-password)); `OPAQUE_SERVER_SETUP` and the reset procedure in [deployment](../deployment.md) and `.env.example`.
- Account migration screen and endpoint; classic credentials only reach that screen.

Verification against a local deployment: the password never appears in any request body (browser network capture); a password change keeps data readable; a reset link issued from the CLI works once and expires; reset with a recovery key and reset from another unlocked device both keep every chat readable, and the device secret never appears in any request; reset with neither yields new keys and locked personal data that a later recovery key restores; login with an unknown email is indistinguishable from a wrong password.

**Done (2026-11-08, migration 2026-11-09).** Hooks, flows, `auth:issuePasswordResetLink`, `OPAQUE_SERVER_SETUP`, explicit Better Auth rate limiting (database storage, client address from Convex request metadata or from the web proxy with `AUTH_PROXY_SECRET`), a 256 KiB auth body bound, and a same-site `Origin` requirement on OPAQUE endpoints (plugin finding F7). Classic sign-up is disabled; classic accounts migrate through "Set up encryption" (below). Making that screen blocking belongs to the content cutover (phase 9).

Verified on an isolated local deployment, over HTTP with the real client plugin and in Chromium: sign-up with recovery-key confirmation; sign-in unwraps the same AMK and export key as sign-up; neither the password, the export key nor the recovery words appear in any request body; wrong password and unknown email both answer `INVALID_CREDENTIALS`/401 ("Invalid email or password."); password change keeps the AMK, revokes other sessions, rejects the old password and rejects a rewrap naming another identity; a CLI reset link carries its token in the fragment, which the page removes from the address bar, and works once; reset with the recovery key, with another unlocked device (slot taken once) and with new keys (new fingerprint; the old identity is kept as `retired`) all complete; regenerating the recovery key works; sign-in is rate-limited per client address (6th attempt 429, another address unaffected); OPAQUE POSTs with a cross-site or missing `Origin` get 403. Not verified: reset link expiry after one hour, the "later recovery key restores personal data" path (nothing encrypted exists yet), and the client address a cloud (non-local) Convex deployment reports.

**Plugin 0.2.0 and account migration (2026-11-09).** Radium pins `@alkalines/better-auth-opaque` 0.2.0 (lockfile integrity matches the reviewed release). Client: both key-stretching allowlists pinned to `rfc-recommended`; Radium's own challenge guard is removed (the plugin now parses and bounds challenge responses). Server: `disableSignUp: false` (Better Auth's flag would now also close OPAQUE sign-up), hooks accept the `attach` flow and enrolment links (`credentialVersion: null`), a per-account budget of 30 password attempts per hour (`accountRateLimit`, keyed by the plugin's email HMAC, identical for unknown emails), `attach.requireCurrentPassword: true`, and reset links issued with `revokePrevious` and `allowEnrolment`. Web: classic sign-in continues to "Set up encryption" (`/auth/setup-encryption`, attach with a new password and recovery-key confirmation); the Window chip links there. Also fixed: before hydration, a form submitted with Enter was sent natively as a GET with the password in the URL; the root document now cancels submits until React has hydrated.

Verified on the isolated local deployment, over HTTP with the real 0.2.0 client and in Chromium: OPAQUE sign-up stays open; password change returns a new session (caller stays signed in, other sessions revoked); attach refuses a reused or wrong classic password, then migrates (keys ready, classic password and other sessions gone, OPAQUE sign-in opens the same AMK); a new reset link revokes the previous one; an enrolment link for a classic account verifies with no keys, completes with new keys, works once and removes the classic password; the per-account budget refuses the 31st attempt from 31 different addresses, identically for an unknown email, without affecting other accounts; in the browser, legacy sign-in → Set up encryption → unlocked with a fingerprint that survives sign-out and OPAQUE sign-in, the reuse error shows, and a later password change keeps the tab signed in; with app scripts blocked, Enter on the sign-in form no longer puts the password in the URL (without the guard it does). Not verified: forms when JavaScript is disabled entirely (the native GET still leaks there; the app does not work without JavaScript), and the content side of migration (phase 9).

**Classic accounts from the normal sign-in form (2026-11-10; plugin side 2026-11-11, release pending).** The separate "Legacy account (before encryption)" form and the sign-in and unlock "Require my password to read past chats" checkboxes are removed; the setting lives only in Settings → Security. Sign-in reacts to the plugin's `CLASSIC_CREDENTIAL` answer by signing in classically with the same password and opening "Set up encryption" with that password held in memory, so only the new password is asked; it refuses the classic path for emails this device has used with OPAQUE and in the unlock dialog ([Authentication § Migrating Existing Accounts](../E2EE/Authentication.md#migrating-existing-accounts)). The plugin answer (`signIn.revealClassicCredential`, [change request](../research/OPAQUE_Plugin_Classic_Sign_In.md)) is implemented on the plugin's `feat/classic-credential-signal` branch but not released; `packages/backend/convex/auth.ts` enables it. Remaining: release the plugin and pin it in `apps/web` and `packages/backend`. Verified in Chromium against the local deployment with the local plugin build: a classic account goes from the sign-in form straight to "Set up encryption" without retyping its password; an unknown email shows "Invalid email or password." and sends only the OPAQUE challenge (no `/sign-in/email`).

## Phase 5: Workspaces, Chats And Trust

Member and owner keys created by the owner's browser in the same mutation as the workspace, grants, access links with fragment secrets, the optional workspace key phrase, pending requests with trust prompts, trust store sync and rollback detection, safety numbers, signed roster, member removal with epoch rotation, re-granting by any key holder after a reset, chat keys and scope changes.

Verification with two real users on a local deployment: the member cannot open the owner's personal chat and vice versa, even with a client that skips the authorization check; replacing a member's public key directly in the database makes the owner's client show `changed` and refuse to grant; an access link works once, and neither its secret nor the workspace phrase appears in any request (network capture); clearing the owner's browser storage right after creating a workspace and signing in again recovers every key; removal blocks new messages for the removed member and invalidates the old phrase for the new epoch.

**Done (2026-11-12), with phase 6.** Decisions taken in the session: accounts and workspaces without keys keep writing plaintext until the migration (an account with keys cannot create a plaintext chat, except a workspace chat in a workspace without keys); existing workspaces get keys automatically the next time their owner is unlocked; grants are signed by the granter and accepted only when the key matches the owner-signed roster; a third chat visibility, **shared** (creator plus picked members, `chat_members`), changed only by the creator; ACP chats stay personal/workspace until phase 7. `workspaces.create` stays keyless: the AAD and signatures bind the Convex workspace ID, so the browser calls `e2ee.bootstrapWorkspaceKeys` right after (an interrupted client is repaired by the automatic bootstrap). Signatures by identities retired after a reset are looked up with `e2ee.identityKeysByKeyId` and accepted only where the current roster or chat epoch still vouches for them; such chat epochs are rotated before the next client write.

Code: `packages/crypto/src/{box,statements}.ts` (sealed boxes, capsule codec, statements); `packages/backend/src/e2ee/{workspace-contract,workspace-keys,invites,trust-store,chat-keys,chat-scope,responses}.ts` and `src/chatroom/members.ts` with thin exports in `convex/e2ee.ts`; web `apps/web/src/lib/crypto/{trust-store,public-keys,workspace-keys,workspace-proofs,chat-keys,trust-requests,runtime}.ts`, `components/trust/`, `components/workspaces/{workspace-keys,workspace-key-sync}.tsx`, route `/join/$inviteId`. A security review (session-internal) found and the change fixes: telemetry content capture for encrypted chats, unbounded member removal, wrap and grant poisoning by members, oversized wraps, unlimited chat key rotation by members, plaintext attachments in encrypted chats, and turns on chats whose key predates a member removal.

Verified on an isolated local deployment (copy of the repository, fresh data), Chromium for the owner and WebKit for the member: sign-up bootstraps the personal workspace's keys (epoch 1, owner grants, roster); an access link's secret never appears in any request frame (WebSocket and fetch capture on both sides), the link's fragment is removed from the address bar, the member's join verifies the owner by the link (pinned `verified`) and the owner's client replaces the self-grant with an owner-signed grant and a new roster version, a second use of the link fails; the workspace phrase never appears in any request; replacing the member's identity directly in the database (a validly self-signed key the "backend" generated) makes the owner's client show the blocking `changed` dialog with both fingerprints and a safety number, and after Deny no chat is created and nothing is sealed to the forged key; the member cannot open the owner's personal chat (server refuses; no wrap exists for them); removing the member rotates the workspace to epoch 2 with grants only for the owner, deletes the member's `chat_members` rows, marks the shared chat for rekey, and the owner's next write creates chat key epoch 2 for both the shared and the workspace chat with no wrap reachable by the removed member (the epoch-1 phrase is not carried to epoch 2); signing in on a fresh browser profile (IndexedDB, storage and cookies cleared) opens every chat, personal, shared and workspace. Not covered: Firefox and Safari proper, re-grants by a member after a reset, and a sole owner's "Rotate epoch" recovery.

## Phase 6: Chatroom Content

Encrypted titles, attachments and queued prompts written by the client; `/api/aisdk/chat` keeps receiving the full AI SDK history from the client, with file parts carrying a file key; per-turn capsules for the persisted user message, assistant output and titles; message IDs and revisions in `saveChatMessages`; client-side title search; attachment download-decrypt-inline for providers; new chats while locked.

Verification: a full Chatroom turn with tools and an attachment; the Convex dashboard shows only envelopes in `chat_messages`, `aisdk_chats` and File Storage.

**Done (2026-11-12).** `chat_messages` rows carry `messageId`, `revision` and `sealed` (an envelope under a per-turn capsule in `e2ee_capsules`); `/api/aisdk/chat` takes `revisions` and seals only new, changed and response messages to the current chat key, generating the first title in the same request; the client seals queued prompts, renamed titles and forks; attachments are encrypted per file under a capsule with the object key only inside sealed messages (`#rf1.` fragment), and `inlineStoredFiles` decrypts them for the provider in memory. `aisdk.regenerateTitle` takes the decrypted first message from the client. Home decrypts titles and searches them locally.

Verified on the same deployment with a mock OpenAI-compatible upstream: a turn with an image attachment and a tool call (`todo_write`) returned "Image received: yes" (the provider got the decrypted bytes, never a fragment), a second turn wrote only the two new positions (revisions 1, earlier rows untouched), rename stored only a sealed title, and a full database export (`convex export`) contains none of the prompt, reply, todo or title text; the stored attachment is a 175-byte envelope (`01 01 01 …`), not the PNG. The member (WebKit) read the workspace and shared chats after unlocking. Title generation with that mock failed for an unrelated reason: the internal Gateway rejects structured output for custom OpenAI-compatible providers ("JSON response format schema is only supported with structuredOutputs"), as it does for plaintext chats. Not covered: new chats while locked (built, not exercised in the browser), forks.

Verification: an ACP session end to end with only ciphertext in `chat_frames`, `acp_commands` and `acp_interactions`; an unsigned command inserted directly into `acp_commands` is rejected by the Worker; an Edit tool call without a user approval signature is refused; a swapped owner key makes the Worker refuse commands.

## Phase 8: Telemetry And Notifications

Telemetry content sealed to the owner key with one capsule per request, keyed hashes (new deployment secret), client-side rendering and diffs, in-request content export, metadata-only scheduled export; sealed notifications and encrypted Web Push payloads with service-worker decryption when keys are remembered.

## Phase 9: Migration

Custody key in Secret Store; action-driven sealing migration with dry run and paginated verification, sealing to owners' keys where they exist and to custody otherwise; per-user and per-workspace release; operator query for custodial rows and the CLI mutation that ends custody; then a separate narrowing deploy. Nothing is deleted. Running it on any deployment needs explicit authorization (`AGENTS.md`).

Verification on a local deployment with seeded legacy data: a user who sets up encryption months later still reads every old chat; an unmigrated account recovered through a reset link keeps its content; the custody key can be deleted only at zero custodial rows.

## Later: Suite Upgrades

Each upgrade is one session using the procedure in [Keys § Suite upgrades](../E2EE/Keys.md#suite-upgrades); the machinery exists from phase 3.

**Suite 2: hybrid signatures (Ed25519 + ML-DSA-65).** Trigger: WebKit ships ML-DSA in WebCrypto, or the team accepts the pure-TypeScript signer everywhere.

1. Define suite `2` in `packages/crypto`: sign = both signatures, verify = both must pass; native ML-DSA through `SubtleCrypto.supports("sign", "ML-DSA-65")` with `@noble/post-quantum` `ml_dsa65` fallback; FIPS 204 test vectors in every runtime, including a Convex mutation (verification only).
2. Phase 1 (Read) deploy: verifiers accept suite 2. Ship web, Worker and backend.
3. Phase 2 (Add): enable generation in `e2ee_policy`; check `key_upgrades` until active users and Workers have certified suite 2 keys; spot-check that no `changed` prompts appeared.
4. Phase 3 (Prefer): switch writing to suite 2; the runner re-signs rosters, trust stores, Worker certificates and standing auto-approve grants.
5. Phase 4 (Require): after `key_upgrades` shows full coverage, reject Ed25519-only signatures.

Verification: mixed old and new clients during phases 1-3; an Ed25519-only forged command is rejected after phase 4.

**KEM encoding change.** If the RFC replacing `draft-ietf-hpke-pq-05` changes MLKEM768-X25519's encoding, the same steps apply with a new KEM suite; existing capsules are not rewritten.
