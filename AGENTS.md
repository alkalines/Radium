# Radium: agent instructions

## Product boundaries

- **Radium** is the project, not a synonym for any one product. Target self-hosted, bring-your-own-key/account/endpoint operation; do not introduce required hosted services or prepaid billing.
- **Chatroom** is where users communicate with agents. It owns conversations, agent configuration, and execution approvals; it uses Gateway for routing and may use a Radium Worker for host-dependent tools.
- **Worker** executes host-dependent work such as editing files, creating folders, and running commands. Convex coordinates durable state and authorization; it is not the execution host. A connected machine's model endpoint and its Worker execution capabilities are separate concerns.
- **Gateway** is the workspace routing boundary: connect machines/model endpoints, providers, and accounts through a single endpoint, centralizing credentials and use across interfaces and API types. Owner audit support is a product goal, not permission to bypass chat privacy. Do not assume one account or endpoint per provider, or claim planned protocols/routing/auditing are implemented.
- `apps/` owns client applications: Web in `apps/web`, with an Expo React Native app and WatchOS/WearOS support planned. `packages/` owns backend, Worker, components, and reusable code; do not make shared contracts depend on a particular client.

## Commands and setup

- Bun workspace (`apps/*`, `packages/*`); install with `bun install` at the root.
- `bun run dev` builds `worker-component` first, then watches that component, Vite, Convex, and the Worker. Enroll the Worker first (`bun run --cwd packages/worker setup`); without enrollment its startup fails while the other processes continue. Worker restarts discard in-memory previews; claimed tasks are not automatically rerun. See `packages/worker/README.md`.
- Web only: `bun run --cwd apps/web vite:dev` (port 3000). Backend: `bun run --cwd packages/backend dev` (**contacts and updates the selected Convex deployment**). Web build/start: `bun run --cwd apps/web vite:build` / `bun run --cwd apps/web vite:start` (Nitro `.output/server/index.mjs`).
- Frontend env belongs in `apps/web/.env.local`; Convex CLI selection belongs in `packages/backend/.env.local`. Neither sets Convex runtime values. `VITE_CONVEX_URL` is the client origin; `VITE_CONVEX_SITE_URL` is the HTTP origin. `VITE_*` values are public/build-time, never secrets. Required backend runtime values: `SITE_URL`, `SECRET_STORE_KEYS`. Setup details and optional values: `docs/deployment.md` and each package's `.env.example`.
- Root scripts declare `lint` and `format:check`, but tools live in `apps/web` and root resolution can fail. Scoped formatting from the root: `./apps/web/node_modules/.bin/oxfmt --check <paths>` (omit `--check` to write). oxfmt rejects paths containing `..`; do not format unrelated files or hard-wrap Markdown prose.

## Wiring and code ownership

- Web is TanStack Start, not Next.js. Routes live in `apps/web/src/app` (configured in `vite.config.mts`); `apps/web/src/router.tsx` integrates TanStack Router, React Query, and Convex. `@/*` means the owning package's `src/*`, not the repository root.
- Default implementation location is the owning package's `src/`, including backend domain logic, validators, auth policies, and Convex-context handlers. Keep `packages/backend/convex/` for schema/configuration, generated bindings, registration exports, and HTTP entrypoints; prefer thin exports like `convex/workers.ts` → `src/worker/`. Keep database access and authorization together in the owning domain, not split across duplicate utility/integration layers. Existing larger `convex/` files are not a template for new code.
- Prefer maintained libraries, Convex Components for isolated persistence, and `convex-helpers` over homegrown infrastructure. Search existing dependencies and the Convex Components directory before adding a custom implementation; record why reuse does or does not fit. Check self-hosting, maintenance, license, versions, auth, and migration implications; add direct dependencies explicitly. Avoid parallel implementations or abstractions that add more maintenance than they remove.
- HTTP wiring: `packages/backend/convex/http.ts` bridges `src/http/router.ts` through Hono; Better Auth registers separately. Gateway routes (`POST /api/openai/v1/chat/completions`, `GET /api/openai/v1/models`) run on the **Convex site**, not Vite. Chatroom's `POST /api/aisdk/chat` handler is `src/http/aisdk.chat.ts` and reuses Gateway's completion pipeline; do not add a second model router.
- Privileged file/Bash execution belongs in `packages/worker`, not Convex. `packages/worker-component` owns isolated machine-identity persistence, mounted as `workerIdentity`; app policy lives in `packages/backend/src/worker/` with registered exports in `convex/workers.ts` and `convex/worker_tasks.ts`. Machine functions use `workerQuery`/`workerMutation` from `src/worker/machine.ts` and verified `ctx.worker`, not browser-session auth.
- Worker execution directories are selected by owner-authorized backend dispatch on the target machine. Bash cwd is **not a sandbox**. Use `src/worker/` contracts and `packages/worker/src/` implementations as the code-level source of truth; local tests do not establish deployed verifier/transport or browser-to-model execution.

## Code clarity and documentation

- Prefer straightforward code over both dense clusters and fragmented call chains. Use descriptive names, ordinary control flow, and whitespace between meaningful phases; avoid nested ternaries, clever expression chains, and packing unrelated work into one statement. Optimize for understanding, not minimum line count.
- Before adding a helper, search the owning domain and shared packages for the same behavior, including differently named equivalents. Reuse or extend a compatible helper without weakening its contract; do not copy it into another file. Promote genuinely shared behavior to its nearest common owner, not a catch-all utilities module.
- Extract a function when it owns a meaningful policy, isolates a complex operation, or removes real duplication. Keep simple one-use steps inline; do not create pass-through wrappers, chains of tiny helpers, or temporary variables that merely rename a value. A longer cohesive function can be clearer than several one-line functions; split by responsibility, not an arbitrary line limit.
- Use **TSDoc beside declarations** for exported APIs, shared contracts, and non-obvious internal contracts. Explain purpose and relevant ownership/auth assumptions, inputs/outputs, side effects, failures, and retry/idempotency constraints; do not repeat types or add boilerplate tags. Improve missing documentation in the code you touch rather than creating a Markdown mirror.
- Use short **`//` comments immediately above the relevant block** when names/control flow cannot explain why it exists: authorization/revocation checks, ordering or atomicity requirements, retry/streaming hazards, migration fallbacks, protocol quirks, bounds/units, or workarounds. Explain the invariant, reason, or consequence—not a translation of the following line. Add an issue/reference for a workaround when one exists.
- For multi-phase logic, a brief comment can orient the reader at a non-obvious transition; do not label every statement or use comments to excuse tangled code. Prefer clearer names or a simpler structure first. Keep comments accurate when behavior changes; remove stale comments and commented-out code you encounter in the touched logic.
- `docs/` is for plans, decisions, product context, operational guides, and handoffs—not exhaustive function/API descriptions. Keep deployment instructions and environment examples aligned with executable config; link to code rather than duplicating its behavior. Do not hard-wrap prose for visual spacing.

## Verification

- Test observable behavior and meaningful failure/security boundaries, not implementation details, mock call counts, or library behavior. Extend focused coverage for actual regressions; do not add suites simply to increase test count. Preserve useful coverage when consolidating redundant tests.
- Offline `convex-test`/mocked-handler tests are fast regression checks, **not Convex integration verification**. Auth/verifier, component wiring, subscriptions, HTTP, migrations, and Worker transport changes need focused tests against a real isolated Convex deployment (local or authorized remote) and real boundaries. If prerequisites or permission are missing, report integration verification as blocked; do not substitute more mocks or claim end-to-end success. Never use production data for these checks.
- `bun run test` builds the component, then runs **backend tests only** through Vitest's `edge-runtime`: `packages/backend/{src,convex}/**/*.test.ts`; import from `vitest`, not `bun:test`. Focused run: `bun run build:components`, then `bun run --cwd packages/backend test <path-filter>`. This runner does not itself establish deployment-backed coverage.
- Worker tests: `bun run --cwd packages/worker test` runs Vitest unit tests and Bun native edit/Bash engine suites; focused units: `bun run --cwd packages/worker test:unit <path-filter>`. Typechecks: `bun run --cwd packages/worker typecheck` and `bun run --cwd packages/worker-component typecheck`; root/web/backend have no typecheck script. Report exact checks and distinguish unit, native, deployment-backed, and skipped verification.

## Authorization and persisted compatibility

- Usage/cost records are operational estimates, not prepaid charges; do not add new balance/credit dependencies.
- Workspace is the ownership boundary. Owners manage configuration, credentials, API keys, MCP servers, defaults, and telemetry; explicit members use configured models and shared chats. Personal chats stay private to their creator **even from workspace owners**. Reuse `convex/workspaces.ts` and `src/workspaces/policy.ts`; detailed contract: `docs/Radium_Gateway/Ownership.md`.
- Membership is direct `workspace_members` access for existing Better Auth users, with implicit ownership and no invitation acceptance. Better Auth organizations do **not** grant workspace access.
- Legacy `balances`, keys, attribution fields, and Secret Store namespaces are a widen-migrate-narrow bridge. Preserve them until the backfill and all paginated verification checks are verified. Migration entrypoint: `packages/backend/convex/migrations.ts`; do not narrow fields or assume deployment readiness from passing local tests.
- Browser auth wrappers must preserve `authComponent.getAuthUser(ctx)` validation. Components do not inherit app auth/table access: authorize in the app wrapper and pass server-derived identity. Keep browser sessions, Gateway API keys, Worker identities, and upstream credentials distinct; reuse analysis: `docs/research/Convex_Reuse.md`.
- Preserve write-only Secret Store credentials and masked displays. Gateway telemetry is owner-only **and filters other users' private chats**; ownership is not permission to audit private transcripts. Request capture, operational logging, and analytics are separate. Logging owners: `packages/backend/src/logging/server.ts` and `apps/web/src/lib/logging.ts`; reuse bounded contracts, exclude secrets/prompts/responses by default, and keep logging failures non-fatal (`docs/logging.md`).
- Verify protocol support against `src/http/router.ts` and adapters, not the product roadmap. Distinguish protocol adapter, model mapping, endpoint, credential/account, and schedulable upstream; never retry after emitted stream output or repeat side-effecting work without an explicit policy.

## Deployment, generated files, and workflow

- Never hand-edit Convex `_generated/` directories or `apps/web/src/routeTree.gen.ts`. Before changing Convex code, read `packages/backend/convex/_generated/ai/guidelines.md` when present and load the relevant Convex skill for component/auth/migration/performance work.
- Web and Convex deploy separately: web build/start does not deploy backend functions. Select the Convex target from `packages/backend`, configure runtime env on that deployment, and set the matching public web origins before building. Production backend deployment must be an explicit authorized operation, not an incidental check; the operational procedure belongs in `docs/deployment.md`.
- `bun run build:components` builds checked-in bindings locally. `bun run codegen` orders initial component build → Worker component codegen/rebuild → backend codegen and needs deployment access for component analysis; standard codegen does not deploy functions. `convex dev` does update the selected deployment. Review generated diffs; neither codegen nor a build proves deployment health.
- For **offline root API declaration refresh only**, use the guarded Node command in `docs/deployment.md#offline-api-binding-codegen`. It writes only `packages/backend/convex/_generated/api.d.ts`; keep its network guard enabled. It does not refresh data models/server/component bindings or verify a deployment.
- Do not deploy, upload functions, run remote migrations, mutate deployment data, or publish without explicit authorization. Inspect the target and command behavior before running Convex CLI operations.
- Verify container/release paths before recommending them; unresolved workspace-layout issues are tracked in `docs/tasks/09_Workspace_Operations.md`. Do not present an intended or untested path as a working quickstart.
- Work on task branches and integrate through PRs targeting `dev`; do not commit directly to `dev`. Do not commit, push, open/merge a PR, or publish without explicit authorization. Keep plans/handoffs in `docs/tasks/` and distinguish intended work from implemented and verified behavior.
